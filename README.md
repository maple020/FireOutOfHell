# 🔥 FireOutOfHell

> 一款受《杀戮尖塔》启发的 Roguelike 卡牌构筑游戏，使用 Godot 引擎开发。

---

## 📖 游戏简介

**FireOutOfHell** 是一款融合了 Roguelike 随机探索与 DBG（牌组构筑）玩法的单人卡牌游戏。玩家将扮演堕入地狱的灵魂，在炽热的深渊中不断深入，通过收集卡牌、遗物和消耗品来构筑独一无二的战斗牌组，与地狱中的恶魔、亡魂展开回合制策略对决。

每一次爬塔之旅都是全新的体验——随机生成的地图、数百张各具特色的卡牌、变化莫测的敌人与事件，让每一局游戏都充满未知与挑战。

## 🛠️ 开发流程

本节是团队日常开发的实操指南，涵盖环境搭建、目录约定、分阶段路线图、功能扩展步骤与验收标准。设计规范与战斗 UI 方案见下文第一、二部分。

### 环境准备

| 工具 | 要求 |
|------|------|
| Godot Engine | **4.3+**（项目已配置 Forward Plus 渲染） |
| Git | 用于版本管理与协作 |
| 编辑器 | 推荐 VS Code / Cursor + Godot 官方插件（可选） |

**首次启动：**

1. 克隆或下载本仓库到本地。
2. 用 Godot 4.3+ 打开项目根目录（含 `project.godot` 的文件夹）。
3. 等待编辑器完成首次资源导入（自动生成 `.godot/`，已在 `.gitignore` 中忽略）。
4. 按 **F5** 运行，主场景为 `scenes/main/main_menu.tscn`。
5. 确认 Autoload 已加载 `GameManager`（`项目 → 项目设置 → Autoload`）。

### 项目目录结构

```
FireOutOfHell/
├── project.godot              # 项目配置、主场景、Autoload
├── assets/                      # 美术与音频（程序不直接改逻辑）
│   ├── audio/                   # 音效、BGM
│   ├── fonts/                   # 地狱风字体
│   ├── particles/               # 粒子预制
│   └── textures/{cards,enemies,ui}/
├── data/                        # 策划向 .tres 数据
│   ├── cards/                   # 卡牌数据（4张）
│   ├── characters/              # 角色数据（1个）
│   ├── consumables/             # 消耗品数据（5个）
│   ├── enemies/                 # 敌人数据（2普通 + 1 Boss）
│   ├── events/                  # 事件数据
│   └── relics/                  # 遗物数据（12个）
├── scenes/                      # 场景文件
│   ├── main/main_menu.tscn      # 主菜单
│   ├── combat/combat_scene.tscn # 战斗场景与 UI
│   ├── card/card.tscn           # 可复用手牌 UI
│   ├── entities/                # PlayerSoul、Enemy
│   ├── run/                     # 地图、熔炉、商店
│   └── ui/                      # 奖励、结算
├── scripts/
│   ├── autoload/                # 全局单例（GameManager）
│   ├── combat/                  # CombatManager、CombatState、效果、音效
│   ├── data/                    # Resource 脚本
│   ├── entities/                # 实体逻辑
│   ├── run/                     # RunManager、地图生成、存档
│   └── ui/                      # 主菜单、飘字、震动、奖励
└── themes/                      # UI Theme 统一管理样式
```

**职责划分：**

- **策划 / 设计**：主要编辑 `data/*.tres` 与 `assets/`，调整数值与文案，无需改代码。
- **程序**：扩展 `scripts/` 中的系统逻辑、Signal 链路与新场景节点。
- **美术**：产出 `assets/textures/`、`assets/particles/`，并在 `themes/` 中配合 Theme 换肤。

### 日常功能开发指南



#### 新增一张卡牌



1. 在 Godot 中：`资源 → 新建 → CardData`，保存到 `data/cards/xxx.tres`。
2. 填写 `id`、`display_name`、`description`、`cost`、`card_type`、`target_type` 等。
3. 若为新效果类型：在 `scripts/combat/effects/` 增加效果脚本，并在 `CombatManager` 效果队列中注册。
4. 将卡牌 ID 加入对应奖励池或起始牌组配置。
5. 用固定 Seed 进战斗验证数值与描述。

#### 新增一个敌人



1. 新建 `EnemyData` → 保存到 `data/enemies/`。
2. 配置 `max_hp`、`intent_pool` 与美术资源。
3. 在遭遇表或地图节点中引用该 `EnemyData`。
4. 测试各意图是否正确执行、意图 UI 是否清晰。

#### 新增一个遗物 / 事件



1. 新建 `RelicData` 或 `EventData` → 保存到 `data/relics/` 或 `data/events/`。
2. 程序侧：在 `RunManager` 或对应系统中监听获取/选择 Signal，挂载效果逻辑。
3. 策划侧：仅改 `.tres` 文案与数值，避免硬编码 ID。

### 架构与编码约定



**Signal 优先（禁止 UI 直接改战斗数据）：**

```
Card.card_selected  →  CombatManager.play_card()
CombatManager.card_played  →  EffectQueue / UI 更新
PlayerSoul.hp_changed  →  HP 条 Tween
RunManager.run_ended  →  GameManager 切换场景
```



**战斗状态机**：所有输入与 AI 行为必须尊重 `CombatState.State`；仅在 `PLAYER_TURN` 接受出牌，仅在 `RESOLVING` 顺序执行效果队列。

**数据驱动**：平衡性调整优先改 `data/*.tres`；只有在新机制时才扩展 Resource 脚本字段。

**命名规范：**

| 类型        | 约定              | 示例                        |
| ----------- | ----------------- | --------------------------- |
| 场景        | snake_case        | `combat_scene.tscn`         |
| 脚本        | snake_case        | `combat_manager.gd`         |
| Resource 类 | PascalCase        | `CardData`                  |
| 数据 id     | snake_case 英文   | `hellfire_strike`           |
| Signal      | 过去分词/名词短语 | `card_played`, `hp_changed` |

### Git 协作流程



1. 从 `main` 拉取最新代码，创建功能分支：`feature/阶段1-牌堆系统` 或 `fix/能量校验`。

**FireOutOfHell 游戏开发规范与战斗UI完整设计方案**

**项目定位**：一款受《杀戮尖塔》深度启发的单人 Roguelike 牌组构筑游戏。玩家扮演堕入地狱的灵魂，在炽热深渊中不断下坠，通过随机探索、卡牌构筑与回合制策略战斗，打造独一无二的“罪孽牌组”，最终突破或征服地狱。核心体验为**高重玩性 + 每局独特构筑故事 + 清晰即时反馈**。

------

### 第一部分：开发规范（Development Guidelines）



#### 1.1 游戏愿景与核心设计原则



- **核心体验目标**：让玩家在每局Run中感受到“我的牌组正在变强”“每一次选择都有重量”“失败后立刻想再来一局”。

- 设计原则

  （全员必须内化）：

  - **有意义的选择**：地图路径、卡牌奖励、遗物获取、休息决策均需有明确利弊。
  - **透明深度**：战斗信息清晰可见（尤其是敌人意图），但组合与时机产生高深度。
  - **风险-回报平衡**：精英战、事件、路径选择必须让玩家权衡当前实力与未来潜力。
  - **数据驱动**：所有卡牌、遗物、敌人、事件、地图规则必须可通过配置表/资源文件快速调整。
  - **公平随机 + 可复现**：必须支持种子（Seed）系统，同一种子下地图与奖励完全一致，便于测试与社区分享。

#### 1.2 核心玩法循环（Core Loop）



**主循环（一局完整Run）**：

1. 开始 → 选择初始“堕落形态”（角色/起始遗物变体）+ 地狱祝福（类似Neow）。
2. 进入**地狱层级地图**（多层深渊结构，可参考但不完全复制Slay the Spire三幕）。
3. 在节点间选择路径：
   - 战斗节点（普通/精英/首领）
   - 事件节点（叙事+机械选择）
   - 熔炉节点（休息回血 或 锻造升级/移除卡牌）
   - 黑市节点（用灵魂碎片购买卡牌/遗物/消耗品）
   - 诅咒宝箱（高风险高回报遗物）
4. 战斗胜利后获得**卡牌奖励**（3选1或更多）+ 灵魂碎片 + 可能遗物。
5. 每深入一层难度递增，最终挑战**地狱君主**或特定终局Boss。
6. 死亡或胜利 → 结算 + 新Run。

**战斗次循环**：玩家回合（规划+打牌）→ 敌人回合（意图执行）→ 状态结算 → 下一回合。

#### 1.3 主要系统规范



- **地图与探索**：程序生成 + 规则约束（路径长度、精英密度、事件权重）。支持多层深渊结构，每层有主题（愤怒层、贪婪层等）。
- **牌组构筑**：初始牌组 + 战斗奖励 + 黑市购买 + 锻造升级/移除。强调“围绕本局随机奖励构建”，而非固定套路。
- **遗物系统**：整局永久生效的强大修改器（诅咒系、火焰系、灵魂系）。获取途径多样，部分有条件触发。
- **消耗品**：战斗中使用，槽位有限（建议3格），提供爆发或解场能力。
- **难度系统**：类似Ascension的层层进阶修改器 + 可选更高难度模式。
- **随机性**：地图生成、奖励池、事件分支、敌人意图均受种子控制。

#### 1.4 技术架构与Godot实现原则（开发必读）



- **强烈推荐数据驱动**：使用 `Resource`（.tres/.res）定义 `CardData`、`EnemyData`、`RelicData`、`EventData`。便于策划快速迭代，无需改代码。

- **状态管理**：推荐使用 `Node` + `Signal` 解耦，或引入轻量状态机（FiniteStateMachine）。战斗内必须有清晰的 `CombatState`（PlayerTurn / Targeting / Resolving / EnemyTurn / Animation）。

- 场景结构建议

  ：

  - `Main`（根节点）
  - `RunManager`（管理整局Run状态、地图、牌组、遗物）
  - `CombatScene`（独立场景，包含所有战斗UI与逻辑）
  - `Card`（可复用场景，带 `CardData` 引用 + 信号）
  - `Enemy` / `PlayerSoul`（战斗实体）

- **信号优先**：卡牌打出、资源变化、状态应用等全部通过 `Signal` 广播，UI与逻辑完全解耦。

- **存档**：必须支持完整Run状态序列化（当前牌组、遗物、地图位置、HP、种子）。

- **性能**：战斗内大量粒子与动画必须使用对象池 + `Tween` + `AnimationPlayer` 优化。

#### 1.5 平衡与测试原则



- 每角色/起始形态至少有3条以上 viable 构筑方向。
- 必须避免“必胜构筑”或“无解死亡”。
- 重点测试：意图系统清晰度、卡牌连锁反馈、地图路径选择权重、遗物与卡牌协同强度。
- 遥测建议：记录每局胜负、死亡原因、常用构筑、关键决策点。

#### 1.6 MVP范围建议（第一阶段）



- 1个完整可玩角色 + 基础牌池 + 核心战斗循环
- 基础地图生成 + 3种节点类型
- 遗物与消耗品各10+个
- 完整种子系统 + Ascension 0-5
- 战斗UI达到可用+美观程度

### 第二部分：战斗UI完整设计方案（Battle UI Design）



**设计目标**：在**地狱炽热、压抑而富有张力**的视觉风格下，实现**信息清晰、操作流畅、反馈即时、策略易读**的战斗界面。参考《杀戮尖塔》经典范式，但进行地狱主题重构与Godot适配优化。

#### 2.1 整体布局与视觉语言（美术重点）



**推荐布局**（从上到下、从左到右）：

- **顶部**：层级信息 + 当前回合数 + 种子显示（可选）。
- **左侧**：玩家灵魂（PlayerSoul）立绘/模型 + **生命条（Ethereal Essence）** + **灵魂护盾（Block）** + 状态图标区。
- **中央偏右**：敌人区域（支持1-3个敌人，可横向排列或根据数量动态布局）。每个敌人上方显示**意图图标**（火焰剑、诅咒锁链、熔岩喷发等）。
- **右侧/顶部**：**地狱能量（Infernal Energy）** 显示区（建议用3-4个熔岩球体或数字+火焰特效）。
- **底部**：**手牌区**（扇形或水平排列，5-8张）。手牌下方或右侧为**弃牌堆**、**抽牌堆**、**永劫堆（Exhaust）** 图标 + 数量。
- **右下角**：**结束回合** 按钮（火焰风格，按下时有燃烧动画）。

**视觉语言规范**（美术团队必须遵守）：

- 主色调：深黑、血红、熔岩橙、暗金、灰烬白。
- 卡牌框架：带燃烧边缘、罪孽纹路、不同稀有度发光强度（普通=暗红，稀有=金红，传说=白金熔岩）。
- 字体：推荐带轻微锋利感的哥特/地狱风字体，关键数字使用高对比发光效果。
- 粒子与特效：战斗中必须有大量**余烬、烟雾、锁链断裂、熔岩溅射**。卡牌打出时有火焰拖尾与爆炸感。
- 状态图标：统一圆形/六边形底框 + 地狱符号（易伤=裂纹火焰、虚弱=锁链缠绕、中毒=绿色毒雾等）。

#### 2.2 玩家回合选择界面



- 手牌默认以**扇形**或**水平微弧**排列，间距适中。
- **悬停（Hover）**：卡牌向上浮起 + 轻微放大 + 右侧弹出完整描述Tooltip（支持BBCode关键词高亮）。合法目标的敌人轮廓变为**熔岩红**高亮。
- **选中**：卡牌进一步放大 + 边缘强烈燃烧效果。能量不足或无合法目标的卡牌整体变暗 + 红色锁链覆盖。
- **目标选择**：点击卡牌后，鼠标变为**燃烧锁链准星**。点击敌人确认释放；可右键或点击空白取消。
- **能量检查**：能量不足时卡牌不可选中，Tooltip提示“需要X点地狱能量”。

#### 2.3 敌人行动反馈机制



- **意图预览**：每个敌人头顶常驻显示意图图标 + 数字（例如“熔岩喷发 12”“诅咒锁链 3层”）。意图在敌人回合开始或特定时机更新。

- 行动执行

  ：

  - 意图图标闪烁 → 敌人播放攻击/施法动画。
  - 伤害以**红色熔岩数字**从敌人飞向玩家，伴随屏幕轻微震动与火焰粒子。
  - 格挡吸收以**暗金护盾破碎**特效表现。
  - 状态应用时，状态图标从敌人飞向玩家或直接出现在状态栏，带对应粒子。

- **死亡反馈**：敌人身体崩解为熔岩与黑烟，伴随锁链断裂音效，实体从战场移除。

#### 2.4 资源条更新逻辑



- **生命条（Ethereal Essence）**：左侧玩家灵魂下方，深红底 + 亮红填充。受伤时从右向左减少 + 红色火焰粒子喷溅；回血时绿色灵魂光效。
- **灵魂护盾（Block）**：在生命条上方或覆盖一层半透明暗金护盾条。优先吸收伤害，护盾破裂时有明显破碎动画。
- **地狱能量**：右侧或手牌上方显示3-4个**熔岩球体**（当前点亮数量 = 当前能量）。消耗时球体暗淡 + 火焰熄灭动画；获得时球体重新点燃 + 火星迸发。
- **状态栏**：玩家与每个敌人下方/上方显示状态图标 + 层数。鼠标悬停显示详细效果描述。
- **更新原则**：所有数值变化必须在**0.2-0.4秒**内完成平滑Tween过渡，关键变化（归零、过量、致命）必须有强调特效与音效。

#### 2.5 卡牌部署与技能释放交互流程



1. 玩家回合开始 → 重置能量 → 抽牌至上限 → 更新所有卡牌可打出状态。
2. 玩家浏览与选择卡牌（Hover → Click）。
3. 合法性校验（能量 + 目标类型）。
4. 释放：卡牌从手牌位置**飞向目标**（带火焰拖尾），同时播放对应特效与音效。
5. 效果结算 → 伤害/治疗/状态数字弹出 → 资源条与状态图标更新。
6. 卡牌去向：普通卡进入弃牌堆（灰烬效果）；消耗卡进入永劫堆（黑色火焰吞噬动画）；特定卡可保留在手牌。
7. 连锁效果自动入队处理，UI按顺序播放动画。

**取消与容错**：右键/ESC取消选中；打牌过程中点击其他卡牌可切换。

#### 2.6 动画、特效与音效指引



- **卡牌动画**：必须使用 `AnimationPlayer` 或 `Tween` 实现流畅飞行动画 + 缩放 + 旋转。
- **粒子系统**：推荐 Godot `GPUParticles2D` 或 `CPUParticles2D`，预制常用特效（火焰拖尾、熔岩爆炸、护盾破碎、灵魂逸散）。
- **音效分类**：卡牌播放音、伤害音、状态应用音、意图更新音、回合结束音。建议分层混音（环境燃烧声 + 战斗音效）。
- **屏幕反馈**：大伤害时轻微屏幕震动（`Camera2D` shake 或 `Tween` 位置偏移）。

#### 2.7 Godot技术实现建议（开发重点）



- 使用 `CanvasLayer` 管理UI层级（战斗UI放最高层）。
- 手牌区推荐 `HBoxContainer` + 自定义 `Card` 场景（带 `TextureRect`、`RichTextLabel`、`Button`）。
- 资源条使用 `TextureProgressBar` + `Tween` 实现平滑数值变化。
- 所有可交互元素必须通过 `Signal` 与 `CombatManager` 通信（例如 `card_played(card_data, target)`）。
- Tooltip 推荐使用 `Popup` 或自定义 `Control` 节点，鼠标位置动态跟随。
- 支持键盘快捷键（数字键选卡、Enter结束回合）作为进阶功能。
- 主题（Theme）资源统一管理所有UI样式，便于后期换肤或DLC。

#### 2.8 验收标准与测试要点



- **信息清晰度**：新玩家在3分钟内能理解意图系统与资源含义。
- **操作流畅度**：从选中卡牌到效果结算全流程 ≤ 1.5秒（动画可跳过选项除外）。
- **视觉反馈完整**：每一次数值变化、状态应用、卡牌释放都有对应视觉+音效。
- **性能**：10个以上粒子系统同时运行时帧率不低于50fps（中低配测试）。
- **可访问性**：支持色盲模式（图标+颜色双编码）、字体大小可调、控制器支持（后期）。
- **测试 checklist**：悬停反馈、目标高亮、能量不足状态、连锁效果播放顺序、死亡动画、回合切换流畅度。
